## 一、吞吐显示方案（核心问题：硬件卸载导致内核计数器盲区）

背景：`flow_offloading_hw=1` 时，转发流量在 PPE 硬件直通，netdev 计数器不可
见（实测全速下载时 pon0 仅 339 kbps）。固件逆向已确认 PPE 驱动自带硬件字节
计数器（见固件分析报告 §五）。

### 方案 A：读取 PPE debugfs —— ❌ **已排除**

用户实测 `/sys/kernel/debug/ppe/status` 文件不存在；固件逆向确认该文件仅在
`an7581_npu_ready` 与 `an7581_npu_has_ppe_stats` 双双通过时才创建，本平台
NPU 统计通道未就绪。同一设备上 `conntrack --counter`、`nft list flowtables`
均无输出。**硬件卸载流量在用户态无可信字节来源。**

### 方案 E：luci.client-rates（conntrack 记账）—— ✅ **已验证，v1.3.0 默认采用**

厂商 rpcd 插件提供 `luci.client-rates get {"addresses":[…]}`，返回 conntrack
字节级记账（含硬件卸载流量），实测 NAS 累计下载 25.7 GB 可见。

主题实现（v1.3.0）：吞吐口径优先级 ① conntrack 差分（精确）→ ② 内核计数器
→ ③ XGEM 估算，取三者最大；采用精确口径时界面标注「conntrack 记账（精确）」。
ACL 已在 `luci-theme-falcon.json` 中授权 `luci.client-rates [get]`。

### 方案 D：关闭硬件卸载（精度最高，需用户自行操作）

在 LuCI → 网络 → 防火墙 → 常规设置中关闭「软件流量分载」与「硬件流量分载」。
关闭后内核计数器恢复工作，主题现有的精确口径立即生效。
代价：转发改走 CPU，CPU 占用上升、高负载时峰值速率可能下降。

### （原方案 A 记录，已排除）读取 PPE debugfs

- 读取 `/sys/kernel/debug/ppe/status`（若存在）解析 `bytes=%llu` /
  `bridge_bytes=%llu`，或 `bind_rate` 的 `lan_forward/wan_forward`；
- 实施方式：新增 ACL 授权的只读辅助脚本（模式与 `falcon-wifi-temp` 完全
  相同：单一脚本、固定路径、零参数、输出 JSON）；
- **风险**：debugfs 读取会触发驱动向 NPU 协处理器发统计查询命令
  （`NPU PPE statistics command`）——这是驱动自身设计的读路径，但鉴于事故，
  **执行前必须由用户自行验证**：
  1. 用户在路由器上手动执行一次
     `cat /sys/kernel/debug/ppe/status`（或确认文件存在）；
  2. 观察 30 秒确认设备稳定；
  3. 用户明确回复同意后，我才部署对应辅助脚本。
- 额外收益：`lan_forward/wan_forward` 计数还可区分 LAN↔WAN 方向。

### 方案 B：ponctl XGEM 帧率估算（零新增风险，推荐先行）

- `ponctl status --json` 的 `counters.xgem_rx / xgem_tx` 是 XPON MAC 硬件层
  帧计数器（位于 PPE 之下，**硬件卸载流量照常计数**，实测 NAS 全速下载时
  5 秒 +249,251 帧）；
- 计算：帧率 × MTU（1500）× 8 ≈ 估算 Mbps，界面明确标注「估算值」；
- 路由器侧改动：零（该调用已在轮询中）；
- 局限：混合小包流量时估偏高，纯 ACK 场景估偏低——作为趋势显示足够，
  作为精确计量不足。

### 方案 C：诚实显示（零风险兜底）

- 硬件卸载启用时，吞吐格显示「硬件加速已启用 · 内核计数不可见」；
- 关闭硬件卸载（用户自行在防火墙设置中操作）时自动恢复精确数值。

### 建议

- 短期：方案 B + C 组合（估算值 + 标注），无任何路由器侧变更；
- 长期：若用户愿意承担方案 A 的一次性人工验证成本，切换到 A 获得精确值。

## 二、插件开发能力清单（基于固件分析）

平台已具备的可编程接口与现成示范（详见固件分析报告 §六）：

1. **ucode view 插件范式已打通**：本主题的 overview / topology 两页即为完整
   范本（menu.d JSON + ACL JSON + rpc/轮询/渲染），可直接复制起步；
2. **遥测数据源**：ubus 标准 family（network/system/iwinfo/luci 定制）、
   ponctl（genl xpon）、qmodem（蜂窝）、nikki（mihomo REST）；
3. **未开发的现成数据源**（可做新插件的点）：
   - `luci.getSwconfigPortState`（若交换机驱动支持，可做端口级详细状态）；
   - qmodem-smsd 短信库 → 短信通知插件增强；
   - nikki/mihomo REST API → 连接级流量可视化（zashboard 已示范）；
   - hqos（`airoha-hqos-v1`，PPE 驱动内置 HQoS 引擎，`max_clients/queues/
     max_rate` 参数已内建）→ 做 UI 化的网速限速管理；
4. **约束**：不碰 proc/debugfs（除非按方案 A 流程单独审批）。

## 三、主题健壮性改进（基于本次教训）

1. **采样架构（已完成）**：单次无参 `network.device status` 全量差分，消灭
   重复采样互踩（吞吐 190 kbps bug 的根因）；
2. **接口全动态发现（已完成）**：WAN 三层设备走 `network.interface dump`，
   WAN 物理口走 `getBuiltinEthernetPorts`，LAN 角色用桥接成员表校准，Wi-Fi
   射频由辅助脚本 `iwinfo` 自动枚举——零硬编码（用户指出的正确问题）；
3. **速率单位（已完成）**：统一 Mbps，自适应精度；
4. **待做清单**：
