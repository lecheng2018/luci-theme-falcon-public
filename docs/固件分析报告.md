## 四、/proc/whnat_ctrl 家族（变砖接口，**永久黑名单**）

`mt_whnat.ko` 创建 `/proc/whnat_ctrl/{tracer, whnat1/{cfg, cr, ctrl, rx, stat,
tx, wdma, wed}}`。逆向结论：

- `ctrl` 的使用说明（模块内置字符串）：
  `echo [0:HW_TX_EN |1:CR_MIRROR_EN] [0:FALSE|1:TRUE] > ctrl`
- 处理函数 `whnat_proc_ctrl_handle` / `whnat_proc_ctrl_write` 将输入解析后
  **直接写 WED/WDMA/PCIE 硬件寄存器**（`Write addr (%x)=%x`），并有完整的
  复位失败序列字符串（`wed_tx_dma reset fail` 等）——与变砖现象完全吻合；
- `cr` 文件同样具备寄存器读写能力（`Read addr (%x)=%x`）；
- **整个目录族都不是遥测接口，写入等同硬件寄存器写操作**。

## 五、硬件流量计数器盘点（吞吐显示问题的答案）

### 5.1 为什么内核计数器看不到卸载流量

`flow_offloading=1` 且 `flow_offloading_hw=1` 时，PPE 把已建立的转发流整体
下沉到硬件：数据包路径为「交换芯片 ↔ PPE ↔ XPON MAC」，**不经过 Linux 协议
栈**。因此 `pon0` / `pon0.66` / `pppoe-wan` / `br-lan` / `lan*` 的 netdev
计数器只反映未卸载的小流量（DNS、短连接等）。实测（NAS 全速下载时）：

```
pon0      ↓ 339 kbps   （实际应为数百 Mbps）
pppoe-wan ↓ 328 kbps
lan1      ↓ 77  kbps ↑ 324 kbps
```

conntrack 字节统计（nf_conntrack_acct）同样不统计已卸载流——实测增量仅
398 kbps。

### 5.2 各计数源一览

| 源 | 内容 | 能否看见卸载流量 | 安全性 | 位置 |
|---|---|---|---|---|
| netdev 统计（ubus network.device status） | 主机路径流量 | ❌ | 高 | 标准 |
| **PPE debugfs `bind_rate`** | `ppe%u: l2b=%u l3=%u` 汇总（实测所见） | 待运行时验证 | 中（debugfs 读） | `/sys/kernel/debug/ppe/bind_rate` |
| **PPE debugfs `status`** | **`flows/added/deleted/rejected/bound/bind_total/packets/bytes`、`lan_forward/wan_forward`、`bridge_bytes`、USB offload 计数** | ✅（PPE 硬件计数） | 中（debugfs 读；依赖 NPU 固件就绪，读取会向 NPU 发统计查询命令） | `/sys/kernel/debug/ppe/status` |
| PPE debugfs `hqos_clients` | HQoS 客户端/队列统计 | — | 中 | `/sys/kernel/debug/ppe/hqos_clients` |
| XPON debugfs（pon0） | FEC 纠错统计（`error_bytes/codewords`）、线路状态 | 仅 FEC 错误字节，非业务流量 | 中 | `/sys/kernel/debug/airoha-xpon-pon0/*` |
| ponctl `status --json` | XGEM 帧计数（`xgem_rx/xgem_tx`）、光功率、温度、注册状态 | ✅（帧计数，PPE 之下，硬件层） | **高**（文档化 CLI，Rust + generic netlink `xpon` family 纯查询） | 官方 CLI |
| ethtool -S | 驱动未提供（pon0「no stats available」） | ❌ | — | 已确认不可用 |

> 注：`bind_rate` / `status` / `hqos_clients` 三个文件名在
> `an7581-bsp-ppe.ko` 的文件名表中连续出现（同一 debugfs_create_file 组）。
> 运行时 `ls /sys/kernel/debug/ppe/` 曾只见 `bind_rate`——`status` 与
> `hqos_clients` 可能按条件创建（依赖 NPU 固件就绪或 hqos 活动），需运行时
> 确认（**须用户批准后才可执行**）。

### 5.2b 决定性证据：硬件卸载是固件**故意默认开启**的

`/etc/uci-defaults/99-firewall4-an758x-offload`（固件自带，安装时自动执行）：

```sh
case "$DISTRIB_TARGET:$(uname -r)" in
	airoha/an7581:5.4.*|airoha/an7583:5.4.*) ;;
	*:5.4.*) offload=0 ;;
esac
uci set firewall.@defaults[0].flow_offloading="$offload"
uci set firewall.@defaults[0].flow_offloading_hw="$offload"
```

而 `/etc/config/firewall` 的 defaults 段固化为：

```
option flow_offloading     1
option flow_offloading_hw  1
```

即：**在 AN7581 + 5.4 内核上，硬件卸载恒为开启，且被厂商显式承诺为支持
路径。** 这不是可选项，是平台设计。

### 5.2c 用户态实测：标准 netfilter 接口同样看不到

用户按方案自行执行（只读）：

| 命令 | 结果 |
|---|---|
| `conntrack -L --counter \| grep -i hw_offload` | 无输出 |
| `conntrack -C` / `nft list flowtables` | 无输出 |
| `/sys/kernel/debug/ppe/status` | 文件不存在（NPU 统计能力检测未通过） |

结论：**该平台上硬件卸载流量的字节数，在用户态没有任何可信来源。**
`nf_flow_table.ko` 虽导出 `flow_offload_hw_stats` 回调，但本平台 PDE/NPU
统计通道未就绪，回调无数据可返回。

### 5.3 ponctl 安全性论证（供决策）

- Rust 实现（panic/错误字符串证实），通过 **generic netlink family
  `xpon`** 与内核通信，`status` 子命令为属性查询（frontend / line /
  registration / datapath / counters），无写入路径；
- `status` 是 `--help` 文档化的官方用法，固件内 luci-app-pon 同款调用；
- 厂商守护进程 `airoha-pond` 常驻并持续读取同一遥测路径；
- 本主题已每 5 秒轮询超过一天（上千次），期间经历链路重注册两次，无异常。

### 5.4 结论：只有两条可行路线

| 路线 | 做法 | 代价 | 精度 |
|---|---|---|---|
| **B（已实现）** | XGEM 帧率 × MTU 估算，界面标注「估算」 | 零 | 趋势准确，绝对值有 ±10~15% 偏差 |
| **D（需用户自行操作）** | 在 LuCI 防火墙设置里**关闭**「软件流量分载」与「硬件流量分载」 | 关闭后 CPU 占用上升、峰值吞吐可能下降 | 精确（内核计数器恢复工作，现有代码路径即刻准确） |

方案 A（读 PPE debugfs）已排除：`status` 文件在本平台不创建。

## 五之二、设计中的「在线主机」统计：真相与可复用方案

design 主题的「在线主机」面板（per-client 上传/下载速率、总流量、连接数）并非
标准 LuCI 功能，而是 **QWRT 定制 rpcd 插件** 提供的。固件逆向得到完整证据链。

### 6.1 服务与实现位置

| 项 | 内容 |
|---|---|
| ubus 对象 | `luci.client-rates`（方法 `get`，参数 `addresses`） |
| ubus 对象 | `luci.client-web`（方法 `get`，客户端端口探测） |
| 实现二进制 | `/usr/lib/rpcd/luci.so`（ELF 共享库，66,121 字节） |
| 关键符号 | `rpc_luci_traffic_init`、`rpc_luci_traffic_discover`、`rpc_luci_dhcp4_clients`、`rpc_luci_webprobe_init` |
| ACL | `luci-mod-status.json`：`luci.client-rates [get]`、`luci.client-web [get]`、`network.rrdns [lookup]` |

### 6.2 数据源：conntrack 记账，**不是**网卡计数器

`luci.so` 内的字符串证据：

```
/proc/sys/net/netfilter/nf_conntrack_acct   ← conntrack 字节记账开关（读取/检查）
nl_socket_alloc / nlmsg_append / netlink    ← libnl，走 ctnetlink 读取 conntrack
netlink_overrun / netlink_error / truncated_dump / dump_timeout / flow_limit
/tmp/luci-client-traffic.state(.new)        ← 差分状态持久化
LCTRAF1                                     ← 状态文件魔数
source=conntrack  started_ms  interval_ms  window_ms  age_ms  ready
upload  download  totals  traffic  routed_connections
```

算法（据字段推定）：

1. 通过 **ctnetlink** 周期性 dump 全量 conntrack 表（带 `accounting` 字节数）；
2. 与上一次 dump 做**差分**（状态存于 `/tmp/luci-client-traffic.state`，用
   `boot_id` 防止重启后误算），得到每个流的新增字节；
3. 按 **源 IP** 聚合到客户端地址，输出 `rates[ip] = {upload, download, ready, mac}`；
4. 累计量单独维护 `traffic[mac] = {upload, download}` 与 `totals[mac]`；
5. `connections[mac]` 为该 MAC 当前的 conntrack 条目数。

关键点：**conntrack 记录的是流级字节数，与流量是否被 PPE 硬件卸载无关** ——
流表在建立时由内核记账，后续硬件转发仍归属同一 conntrack 条目。这就是为什么
design 面板能显示实时速率，而 netdev 计数器不能。

### 6.3 与我们此前结论的关系

| 结论 | 是否仍然成立 |
|---|---|
| netdev 计数器看不见卸载流量 | ✅ 成立 |
| `/sys/kernel/debug/ppe/status` 不存在 | ✅ 成立（NPU 统计能力未就绪） |
| **conntrack 看不见卸载流量** | ❌ **推翻** —— 我们当时的验证方法有误 |

此前用户实测 `conntrack -L --counter | grep -i hw_offload` 无输出，原因不是
conntrack 无记账，而是：

1. `nf_conntrack_acct` 默认可能为 0——没有开启字节记账时，字节字段根本不采集；
2. `conntrack` 命令行工具的 `--counter` 输出格式与 `grep hw_offload` 的匹配
   方式不匹配（工具显示的是 `[HW_OFFLOAD]` 标记在状态列，且需 `-o extended`）；
3. 该面板读取的是 `luci.client-rates` 这个**厂商已封装好的**接口，内部自己
   处理了开关检查、netlink dump 与差分。

### 6.4 可复用方案（**这是精确吞吐的正解**）

**方案 E：复用厂商 `luci.client-rates` 接口** —— ✅ **已验证并实现（v1.3.0）**

```js
var callClientRates = rpc.declare({
    object: 'luci.client-rates',
    method: 'get',
    params: [ 'addresses' ],
    expect: { '': {} }
});
// 返回：{ rates: { "<ip>": {upload, download, ready, mac} },
//         traffic: { "<MAC>": {upload, download} },
//         totals: { "<MAC>": bytes },
//         connections: { "<MAC>": n },
//         warming_up, incomplete, age_ms, source: "conntrack" }
```

优势：
- **精确**：conntrack 字节级记账，不受硬件卸载影响；
- **零风险**：官方 ubus 调用，ACL 已授权给 `luci-mod-status`（本主题已在该
  权限组内）；
- **零成本**：厂商已实现好差分、状态持久化、开机重置、netlink 异常处理；
- 还能顺带提供 **per-client 速率**（可做「在线主机」面板）。

### 6.4b 运行时验证结果：**接口可用，数据完整**（2026-11-19 用户实测）

```sh
ubus call luci.client-rates get '{"addresses":["<客户端IP>"]}'
```

返回（节选）：

```json
{ "source": "conntrack", "started_ms": 19672, "incomplete": false,
  "interval_ms": 2000, "window_ms": 6000, "age_ms": 1577,
  "rates":     { "<ip>": { "ready": true, "mac": "…", "upload": 652, "download": 9438 } },
  "totals":    { "<MAC>": <累计字节> , … 共 32 台 },
  "traffic":   { "<MAC>": { "upload": <字节>, "download": <字节> }, … },
  "connections":        { "<MAC>": <连接数> },
  "routed_connections": { "<MAC>": <经路由连接数> } }
```

要点：
- `source=conntrack` 确认数据源；
- `totals` 中出现 `<NAS 的 MAC>` 累计 **25.7 GB 下载**——这是 NAS 的实际下载量，
  **netdev 计数器完全看不到**，证明 conntrack 记账覆盖硬件卸载流量；
- `interval_ms=2000 / window_ms=6000` 为内部采样节奏，`ready` 表示该 IP 已就绪。

### 6.4c 参数注意（曾导致误判）

调用时 `addresses` 必须是**纯 IP 字符串数组**：

```sh
# ✅ 正确
ubus call luci.client-rates get '{"addresses":["<客户端IP>"]}'
# ❌ 错误（尖括号是文档占位符，不是命令的一部分）
ubus call luci.client-rates get '{"addresses":["<<占位符>>"]}'
```

后者会被 blobmsg 解析为非法值，返回 `Command failed: Invalid argument`。

需要确认的两点（只读，可由用户执行）：

```sh
# ① 确认记账开关状态
cat /proc/sys/net/netfilter/nf_conntrack_acct
# ② 直接调用该 ubus 接口看返回结构
ubus call luci.client-rates get '{"addresses":["<客户端IP>"]}'   # 换成你要查的客户端 IP
```

若 ② 有正常返回，则本主题的吞吐格可切到**精确口径**（WAN 总速率 = 所有
客户端下载之和，或直接用 `network.device` 之外的 conntrack 汇总），并可新增
「在线主机」页面。
